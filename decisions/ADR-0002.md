# ADR-0002: Phase 2 Sonnet/Opus split + Local Qwen relevance filter -- a meglévő rendszer kiterjesztése

Active (2026-09-01..2026-09-02) -- Phase 2 TASK-0010..0014 COMPLETE; Sonnet split aktív, service restart sikeres, scripted send védve a monitor ön-javító ciklussal

## Context

A Phase 1 (ADR-0001) bevezette a Standard Work skill package-et + persistent state-et, de a tényleges model routing split (Sonnet default + Opus escalation) még nem történt meg: a `.env`-ben minden szint `claude-opus-4-6` volt, a MiniMax proxy-n át. Ez pazarló, mert:

1. **A legtöbb implementációs / refactor feladathoz a Sonnet is elég** -- az Opus minősége csak komplex architektúra / race condition / multi-system integration esetén kell (lásd a ROUTING_POLICY.md szintjeit: L2 Sonnet, L3 Opus)
2. **A Local Qwen (qwen2.5:3b a HA NUC-on) a relevance filter-t ingyen megcsinálja** -- a Context Gate Phase 3-ban a cloud hívás előtt szűri a contextet, így a cloud modell kisebb, sűrűbb inputot kap
3. **A Cloud token budget az Alex-előfizetésből jön** -- a felesleges Opus hívások pazarlás, a Phase 2 cél a költség-hatékonyabb működés

**FONTOS FELFEDEZÉS (2026-09-01, Phase 2 TASK-0013 előkészítés):** a MiniMax proxy NEM a valódi Claude modelleket szolgáltatja. A `claude-sonnet-4-6` / `claude-opus-4-6` modellnevek a proxy belső **`MiniMax-M3`** modelljére képződnek le (bizonyíték: POST /v1/messages `{"model":"claude-sonnet-4-6"}` -> response `"model":"MiniMax-M3"`). A `.env`-ben a nevek maradnak (a kód ezt olvassa), DE a tényleges modell a proxy-n `MiniMax-M3` (lásd `project_minimax_proxy_actual_model.md` memória + PROJECT_MEMORY.md "Cloud model" sor frissítve). A "Sonnet split" elnevezés a kódban marad, de a valóság `MiniMax-M3` split -- a költség-számítások a `MiniMax-M3` proxy ára alapján menjenek.

A Sonnet elérhetőség-teszt 2026-09-01 23:30-kor sikeres volt (HTTP 200, 165 token költség): a service restart biztonságos, mert a proxy válaszol.

A Phase 2 négy fő feladatot old meg:

- **Opus (MiniMax-M3) escalation megőrzése** (az `ANTHROPIC_DEFAULT_OPUS_MODEL` + `ANTHROPIC_MODEL` marad Opus, a strong reasoning szinthez)

## Decision

### 1. Sonnet (MiniMax-M3) split a `.env`-ben (TASK-0010 + TASK-0012)

A `.env` fájlban két változó állítódik Sonnet-re (a proxy-n ez valójában `MiniMax-M3`):

```
ANTHROPIC_DEFAULT_SONNET_MODEL=claude-sonnet-4-6   # TASK-0010 (proxy-n: MiniMax-M3)
DEFAULT_AGENT_MODEL=claude-sonnet-4-6              # TASK-0012 (proxy-n: MiniMax-M3)
```

A többi modell-sor (`ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_OPUS_MODEL`, `MAIN_AGENT_MODEL`) Opus marad -- ezek a strong reasoning + a főágens szintje (a proxy-n ezek is `MiniMax-M3`-ra képződnek le).

A `buildModelEnv` (a `src/web/routes/background-tasks.ts`-ben) a `process.env`-ből olvassa a `MODEL_ENV_KEYS`-ben felsorolt változókat, és a tmux session-ben futó `claude -p` parancshoz exportálja. A Sonnet split csak a **service restart** után érvényesül (a `process.env` a szerver indulásakor rögzül).

**Sonnet elérhetőség-teszt (TASK-0013 előkészítés, 2026-09-01 23:30):** HTTP 200, `"model":"MiniMax-M3"`, 165 token (164 input + 1 output). A proxy válaszol, a service restart biztonságos.

### 2. Local Qwen relevance filter (TASK-0011)

A `src/qwen-router.ts`-hez új függvények kerülnek:

- `RelevanceChunk { id, content }` -- input unit
- `RelevanceResult { id, score }` -- scored output (0.0-1.0)
- `RelevanceFilterOptions extends CompleteOptions { topK? }`
- `relevanceFilter(query, chunks, opts)` -- batch + fallback logikával:
  1. Batch path: egy prompt, top-K JSON válasz (1 round-trip)
  2. JSON parse hiba VAGY kevesebb item: fallback per-chunk classify()
  3. Soha nem dob; teljes hiba esetén üres tömb (a Context Gate "no pre-filter" üzemmódba esik)

A függvény a meglévő `complete()`-t hívja, tehát a Qwen → Anthropic fallback lánc érvényes. Ha a HA NUC Ollama nem elérhető, a relevance filter az Anthropic-re esik (drágább, de működik).

### 3. Service restart ütemezése (TASK-0013)

A Sonnet split csak a service restart után érvényesül. A restart időablaka:

- **TILTOTT**: 02:07-06:00 (a `dream-engine` + `reggeli-napindito` + `reggeli-napindito-send` + `reggeli-monitor-0605` szent időablaka)
- **ENGEDÉLYEZETT**: 22:00-02:00 (a restart időablak a Sonnet split Task-0013-ban) VAGY 08:50-22:00

A restart a Phase 2 TASK-0013-ban történik, a Phase 2 integrációs teszttel együtt (worktree + HA NUC Ollama elérhetőség-ellenőrzés + MiniMax proxy Sonnet elérhetőség-ellenőrzés).

### 4. Context Gate Phase 3-ba halasztva

A relevance filter függvény mostantól elérhető a kódból, de a tényleges integráció (a cloud hívás előtti automatikus relevance filter hívás) a **Phase 3**-ban történik. A Phase 2 célja a Sonnet split + a relevance filter API elérhetősége, a Phase 3 a teljes pipeline (deterministic search + vector retrieval + Qwen relevance + min context assembly).

## Consequences

### Pozitív

- A Sonnet split a service restart után jelentősen csökkenti a cloud költségeket (a legtöbb háttér-jobb Sonnet-en fut, nem Opus-on)
- A relevance filter API elérhető a Phase 3-hoz (a `relevanceFilter()` függvény unit tesztelhető worktree-ben)
- A főágens továbbra is Opus-on fut (a `MAIN_AGENT_MODEL=claude-opus-4-6` marad), tehát a minőség nem romlik
- A relevance filter a Local Qwen-t használja (HA NUC, ingyenes), nem a cloud modellt
- A `.env` módosítás `.gitignore`-ban van, így az érzékeny tokenek (`ANTHROPIC_AUTH_TOKEN`) nem kerülnek git commit-ba
- A Phase 2 dokumentációja teljes: PROJECT_MEMORY.md, ADR-0002, CURRENT_STATE.yaml

### Negatív / kockázat

- A Sonnet elérhetősége a MiniMax proxy-n nem 100%-ig biztos (a `CHAT_MODEL=claude-sonnet-5` más backend-en fut). Ha a Sonnet nem elérhető, a háttér-jobok elbuknak. **Rollback**: `.env` revert + service restart
- A relevance filter batch path a 3B modell JSON képességére támaszkodik -- a fallback path lassabb (N round-trip), de megbízható
- A service restart TASK-0013-ban a 22:00-02:00 időablakban jön, ami most (23:30) azt jelenti, hogy a restart holnap 02:00-02:07 előtt kell megtörténjen (vagy 08:50 után)
- A relevance filter függvény még NINCS használva a cloud hívás előtt -- a tényleges Context Gate Phase 3-ban jön

## Alternatives Considered

### A) Azonnali Sonnet-re váltás minden szinten (beleértve MAIN_AGENT_MODEL)
- **Elvetve**: a főágens (Jarvis) Opus minősége fontos Alex interakcióhoz; a Sonnet nem biztos, hogy elég a komplex döntésekhez
- **Részben alkalmazva**: a DEFAULT_AGENT_MODEL (háttér-jobok) Sonnet-re vált, mert ezek mechanikus feladatok

### B) A relevance filter Anthropic-kel (nem Local Qwen-nel)
- **Elvetve**: pazarlás, a Local Qwen ingyen van a HA NUC-on (LAN, nincs API-költség); a 3B modell elég a classify / relevance feladathoz
- **Alkalmazva**: a relevance filter a Qwen-t preferálja (a meglévő `complete()` fallback lánc), csak Qwen hiba esetén esik Anthropic-re

### C) Service restart azonnal (TASK-0012 után)
- **Elvetve**: a restart nem sürgős, és a 02:07-06:00 szent időablakban nem kockáztatható
- **Alkalmazva**: a restart TASK-0013-ban, a 22:00-02:00 időablakban

### D) A relevance filter hozzáadása a `src/web/routes/background-tasks.ts`-hez (a `buildModelEnv` mellé)
- **Elvetve**: a relevance filter a Context Gate Phase 3-ban fog használódni, nem a háttér-taskok indításakor
- **Alkalmazva**: a relevance filter a `src/qwen-router.ts`-be kerül, mint új API (a Phase 3 hívja)

### E) A DEFAULT_AGENT_MODEL átállítása nélkül, csak az ANTHROPIC_DEFAULT_SONNET_MODEL-re
- **Részben alkalmazva TASK-0010-ben**: az ANTHROPIC_DEFAULT_SONNET_MODEL Sonnet-re vált (TASK-0010)
- **Kiegészítve TASK-0012-ben**: a DEFAULT_AGENT_MODEL is Sonnet-re vált (a háttér-jobok Sonnet-re)
