# ADR-0003: Phase 3 Context Gate pipeline -- opt-in recall filter, full pipeline in src/context-gate.ts

## Status

Active (2026-09-02) -- Phase 3 TASK-0015..0017 COMPLETE; src/context-gate.ts + tests + recall endpoint opt-in integration committed; service restart pending Alex approval.

## Context

A Phase 2 (ADR-0002) bevezette a `relevanceFilter()` függvényt a `src/qwen-router.ts`-ben, de az csak egy függvény volt -- a tényleges hívási hely és a pipeline (deterministic pre-filter + relevance filter + assembly) nem volt meg, és a cloud hívás semmit nem profitált belőle.

A Phase 3 célja kettős:
1. **A pipeline megépítése** -- egy önálló `src/context-gate.ts` modul, ami a candidate set-ből (memória keresés, vector retrieval, file grep) kiszűri a top-K legrelevánsabb chunkot a cloud modellnek.
2. **Egy konkrét integrációs pont** -- a recall endpoint (`src/web/routes/recall.ts`), ahol a memória-visszakeresés eredménye a Context Gate-en átmegy, és a cloud hívás csak a top-K memóriát kapja (nem az összeset).

A Phase 3 a Phase 2-re épít:
- A `relevanceFilter()` (qwen2.5:3b a HA NUC-on) már elérhető batch + fallback útvonallal
- A vector retrieval (`nomic-embed-text` szintén a HA NUC-on) már elérhető `db.ts`-ben
- A hibrid memória-keresés (`hybridSearch` RRF-fel) már él

A hiányzó láncszem: a recall endpoint NEM szűrte a találatokat a cloud hívás előtt. Mind a 50 memória (vagy amennyi a `limit` volt) visszament a hívónak, aki aztán az egészet beadta a cloud modellnek.

## Decision

### 1. Új `src/context-gate.ts` modul (TASK-0015)

A pipeline három lépésből áll, mind a `gateContext(query, candidates, opts)` függvény belsejében:

```
query + candidates (RelevanceChunk[])
  ↓
[1] deterministic pre-filter  (tokenize + keyword score, free, no I/O)
  ↓                      -- ha candidates <= deterministicMax (20), lépés kihagyva
  ↓                      -- ha minden chunk zero-score, top-N by input order fallback
[2] relevanceFilter()        (qwen2.5:3b, batch + fallback, már van)
  ↓
[3] (opcionális) assembleContext() -- join top-K contents into single string
```

Az `assembleContext()` külön exportált, hogy a hívó dönthessen: strukturált `RelevanceResult[]`-t kér, vagy egyetlen összefűzött stringet.

A függvény SOHA nem dob -- ha minden elbukik (relevance filter errors, üres fallback), az input chunkokat adja vissza eredeti sorrendben zéró score-ral ("no pre-filter" degraded mode).

### 2. A recall endpoint integráció (TASK-0016)

A `tryHandleRecall` a `/api/recall?q=<query>&gate=true&gateTopK=5` paramétereket fogadja:
- `gate=true` -- opt-in a Context Gate-re (default `false` a backward compat miatt)
- `gateTopK=5` -- a top-K méret (1-20, default 5)

Ha `gate=true` ÉS van query ÉS a találat > topK:
- A `memories` tömbből `RelevanceChunk[]` készül
- `gateContext()` fut le
- A visszatartott ID-k alapján szűrjük a `memories` listát
- A response-ba bekerül egy `gate: { enabled, before, after, topK }` meta + opcionális `assembledContext` string

Ha a gate elbukik (timeout, Qwen hiba, stb.) -- az eredmény visszamegy szűrés nélkül, csak a `before`/`after` meta jelzi, hogy nem történt szűrés.

### 3. Opt-in, nem default

A backward compat fontos: a jelenlegi hívók (a főágens, a scheduled taskok, a dashboard UI) mind `?gate=` nélkül hívnak, és változatlan viselkedést kapnak. A Phase 3 csak az új `?gate=true` hívóknál aktiválódik. A default-ON-ra váltás Phase 4 (Dynamic Model Escalation) döntése lesz, amikor a Phase 3 hatásáról már van mért adat.

## Consequences

### Pozitív

- A cloud modell a recall endpointból csak a top-K legrelevánsabb emléket kapja, nem az összeset (50 -> 5 tipikus esetben)
- A pipeline determinisztikus része ingyen fut (keyword scoring, nincs modell hívás)
- A Qwen relevance filter a HA NUC-n fut (LAN, ingyen), nem a cloud-on
- A backward compat megmaradt (opt-in)
- A gate metadata (`before`/`after`/`topK`) a response-ban segíti a debuggingot és a Phase 4 metrika-gyűjtést
- Az `assembledContext` string kényelmes a cloud híváshoz: nem kell a hívónak külön joinolnia
- 18 unit teszt a determinisztikus függvényekre (`src/__tests__/context-gate.test.ts`), worktree alatt futtatva

### Negatív / kockázat

- A Qwen relevance filter ~5 másodperc / hívás (a 3B modell CPU-only a HA NUC-on), tehát a recall endpoint 5-10 másodperccel lassabb lesz `gate=true` mellett
- A relevance filter batch path a Qwen JSON képességére támaszkodik -- a fallback path lassabb (N round-trip), de megbízható
- Az opt-in default lassítja a Phase 3 hatásának mérését (csak akkor látjuk a megtakarítást, ha valaki `gate=true`-val hív)
- A Phase 3 NEM érinti a többi cloud hívási pontot (`background-tasks.ts`, `agent-process.ts`) -- ezek Phase 4-5 téma

## Alternatives Considered

### A) Default ON a recall endpointon
- **Elvetve Phase 3-ban**: backward compat risk (a jelenlegi hívók nem várnak 5 másodperces latency-t a recall-ra)
- **Mérlegelés Phase 4-ben**: ha a Phase 3 hatásáról van mért adat, a default ON lehet a jobb

### B) A Context Gate integráció a `background-tasks.ts`-ben (a `buildModelEnv` mellé)
- **Elvetve Phase 3-ban**: a háttér-task promptja előre megírt, a gate kevésbé alkalmazható
- **Alkalmazva Phase 4/5-ben**: a háttér-taskok promptjába beépíthető a "context candidates" mező

### C) A relevance filter külön endpointon (`/api/relevance-filter`)
- **Elvetve**: nem integrálódik semmivel, csak egy wrapper lenne a `relevanceFilter()` köré
- **Alkalmazva**: a `gateContext()` a természetes API, nem kell külön endpoint

### D) A Qwen hívás kihagyása, csak a determinisztikus pre-filter
- **Elvetve**: a Qwen relevancia-becslése lényegesen jobb, mint a puszta keyword score
- **Részben alkalmazva**: a `deterministicMax` opcióval a hívó dönthet, hogy N<=20-nál kihagyja a Qwen-t (ingyen pathway)

### E) A relevance filter eredményét cache-elni (ugyanaz a query + chunk set)
- **Elhalasztva Phase 5-re**: a recall query-k ritkán ismétlődnek pontosan, a cache hatás valószínű kicsi
- **Alkalmazható**: ha a Phase 4 mérés azt mutatja, hogy a Qwen hívás a domináns költség
